## Tổng quan
- Nếu công ty đang sử dụng Jira để quản lý công việc thì hoàn toàn có thể triển khai và vận hành Hệ thống quản lý chất lượng (QMS) theo ISO 9001 trên Jira.
- Tuy nhiên, nguyên tắc quan trọng là:
  - ISO yêu cầu kiểm soát quy trình và bằng chứng thực hiện, không bắt buộc phải dùng biểu mẫu giấy hay phần mềm riêng.
  - Jira sẽ đóng vai trò là nơi quản lý quy trình, hồ sơ và bằng chứng tuân thủ ISO.

### 1. Hiểu đúng yêu cầu của ISO khi áp dụng trên Jira
- ISO 9001 thường yêu cầu doanh nghiệp phải chứng minh được:
  - Quy trình đã được định nghĩa
  - Trách nhiệm và quyền hạn rõ ràng
  - Công việc được thực hiện đúng quy trình
  - Có bằng chứng thực hiện
  - Có kiểm soát thay đổi
  - Có xử lý sự không phù hợp
  - Có theo dõi KPI và cải tiến liên tục
- Jira có thể đáp ứng các yêu cầu này thông qua:
  - Workflow
  - Issue Type
  - Custom Field
  - Approval
  - Permission
  - Dashboard
  - Report
  - Audit Log
  - Attachment

### 2. Xây dựng cấu trúc ISO trên Jira
- Cấp 1: Quy trình (Process)
> Mỗi quy trình ISO được tạo thành một Project hoặc một nhóm issue riêng.

Ví dụ:
```text
Nhóm quy trình
QMS - Quản lý chất lượng
DEV - Phát triển phần mềm
TEST - Kiểm thử
SUP - Hỗ trợ khách hàng
HR - Nhân sự
PUR - Mua hàng
```

- Cấp 2: Thủ tục (Procedure)
> Mỗi Procedure được quản lý dưới dạng:

**Issue Type: Procedure**

Ví dụ:
```text
PR-001 Quy trình phát triển phần mềm
PR-002 Quy trình xử lý lỗi
PR-003 Quy trình đánh giá nội bộ
```

_Trường đính kèm:_
```text
File Procedure ISO
Link Confluence
```

- Cấp 3: Công việc thực thi
> Mỗi lần thực hiện quy trình sẽ phát sinh Issue.

Ví dụ:
```text
TASK-001 Phát triển chức năng Login
TASK-002 Kiểm thử Release 2.0
```

Đây chính là: Hồ sơ chất lượng (Quality Records) mà ISO yêu cầu.

### 3. Thiết kế Workflow đáp ứng ISO

Ví dụ quy trình phát triển phần mềm

Workflow Jira:
```text
Draft
  ↓
Analysis
  ↓
Development
  ↓
Code Review
  ↓
Testing
  ↓
UAT
  ↓
Released
  ↓
Closed
```

**Điểm kiểm soát ISO**: Không cho phép chuyển bước nếu chưa đủ điều kiện.

Ví dụ:

Từ
```text
Development → Code Review
```

Bắt buộc:
```text
Đã nhập effort
Đính kèm source
Reviewer được chỉ định
```
Từ
```text
Testing → UAT
```

Bắt buộc:
```text
Test case hoàn thành
Test report được upload
```
Điều này giúp chứng minh: Công việc được thực hiện theo quy trình đã ban hành.

### 4. Quản lý phê duyệt theo ISO
- ISO yêu cầu nhiều tài liệu và hoạt động phải được phê duyệt.
- Trong Jira có thể xây dựng workflow:
```text
Draft
 ↓
Review
 ↓
Approved
 ↓
Effective
```

Ví dụ:
```text
Tài liệu ISO
Quy trình
Hướng dẫn công việc
Biểu mẫu
```
Bổ sung trường:
```text
Author
Reviewer
Approver
Approval Date
Version
```

Khi chuyển sang trạng thái Approved:
```text
Jira lưu lịch sử
Lưu người phê duyệt
Lưu thời gian phê duyệt
```
Đây là bằng chứng đánh giá ISO rất tốt.

### 5. Kiểm soát tài liệu và phiên bản
- ISO 9001 yêu cầu: Chỉ sử dụng tài liệu phiên bản hiệu lực.
- Giải pháp: Jira + Confluence
  - Confluence quản lý:
    - SOP
    - Procedure
    - Work Instruction
  - Jira quản lý:
    - Workflow phê duyệt
    - Theo dõi thay đổi

Ví dụ:
```text
WI-DEV-001
Version: 3.0
Status: Effective
```

Khi sửa:
```text
Version 4.0
Status: Draft
```

Sau khi Approved:
```text
Version 4.0 Effective
Version 3.0 Obsolete
```

### 6. Quản lý NCR (Non-Conformity)
- ISO yêu cầu kiểm soát sự không phù hợp.

Tạo Issue Type: NCR

Workflow:
```text
Open
 ↓
Investigating
 ↓
Containment
 ↓
Corrective Action
 ↓
Verification
 ↓
Closed
```

Các trường:
```text
Root Cause
Containment Action
Correction
CAPA Owner
Verification Result
```

Khi đánh giá ISO: Auditor có thể xem toàn bộ lịch sử xử lý.

### 7. Quản lý CAPA

Issue Type: CAPA

Workflow
```text
Open
 ↓
Analysis
 ↓
Action Plan
 ↓
Implemented
 ↓
Verified
 ↓
Closed
```

Liên kết với:
```text
NCR
Audit Finding
Customer Complaint
```

Jira hỗ trợ Issue Linking để thể hiện mối liên hệ này.

### 8. Quản lý Audit nội bộ

Tạo Project: Internal Audit

Issue:
```text
Audit Program
Audit Checklist
Audit Finding
```

Workflow:
```text
Planned
 ↓
Conducted
 ↓
Reported
 ↓
Closed
```

Các Audit Finding được liên kết đến:

- NCR
- CAPA
- Risk

### 9. Quản lý rủi ro theo tư duy ISO

ISO 9001 yêu cầu Risk-based Thinking.

Tạo Issue Type: Risk

Các trường:
```text
Probability
Impact
Risk Score
Mitigation Plan
Owner
```

Workflow
```text
Identified
 ↓
Assessed
 ↓
Mitigated
 ↓
Monitored
 ↓
Closed
```

Dashboard theo dõi:
```text
High Risk
Medium Risk
Low Risk
```

### 10. Quản lý KPI và mục tiêu chất lượng

ISO yêu cầu đo lường hiệu quả.

Tạo mục tiêu: Quality Objective

Ví dụ:
```text
Defect Rate < 2%
On-time Delivery > 95%
Customer Satisfaction > 4/5
```

Dashboard Jira hiển thị:
```text
Open Issues
SLA
Resolution Time
Defect Density
Audit Findings
CAPA Closure Rate
```

### 11. Các bằng chứng ISO có thể lấy trực tiếp từ Jira
- Khi đánh giá chứng nhận ISO, có thể trình bày:
  - Bằng chứng tuân thủ quy trình
    - Workflow history
    - Transition history
    - Approval history
  - Bằng chứng thực hiện
    - Issue Record
    - Comment
    - Attachment
  - Bằng chứng kiểm soát thay đổi
    - Change Log
    - Audit Trail
  - Bằng chứng cải tiến
    - NCR
    - CAPA
    - Audit Findings
    - KPI Reports

### 12. Mô hình triển khai khuyến nghị

Một mô hình thực tế khá hiệu quả:

### Kết luận
- Để đảm bảo đúng yêu cầu ISO khi dùng Jira, doanh nghiệp nên áp dụng nguyên tắc:
  - Mỗi quy trình ISO phải được ánh xạ thành Workflow trên Jira.
  - Mỗi lần thực hiện quy trình phải tạo Issue để tạo hồ sơ chất lượng.
  - Kiểm soát phê duyệt bằng trạng thái và quyền hạn trong Workflow.
  - Lưu toàn bộ bằng chứng (file, comment, approval, lịch sử thay đổi) trên Jira.
  - Quản lý NCR, CAPA, Risk, Audit và KPI bằng các Issue Type riêng.
  - Kết hợp Jira với Confluence để đáp ứng yêu cầu kiểm soát tài liệu ISO một cách đầy đủ.

> Với cách triển khai này, khi đánh giá ISO 9001, auditor có thể truy xuất toàn bộ bằng chứng trực tiếp trên Jira thay vì hồ sơ giấy, đồng thời vẫn đáp ứng đầy đủ các điều khoản về kiểm soát quy trình, hồ sơ và cải tiến liên tục.

# GIẢI PHÁP TỔ CHỨC LƯU TRỮ, PHÂN CÔNG THỰC HIỆN ĐỐI VỚI NGHIỆP VỤ QUẢN LÝ VĂN BẢN CỦA DOANH NGHIỆP

---

## I. Mục tiêu áp dụng

1. Chuẩn hóa và tối ưu hóa không gian lưu trữ
    - Số hóa toàn diện: Chuyển đổi tối đa các văn bản, tài liệu giấy sang dạng dữ liệu số, giảm thiểu không gian lưu trữ vật lý và chi phí in ấn.
    - Kho lưu trữ khoa học: Xây dựng hệ thống danh mục, mã hóa và phân loại văn bản (đi, đến, nội bộ) một cách logic, giúp việc tìm kiếm và truy xuất thông tin được thực hiện nhanh chóng.
    - Quản lý vòng đời tài liệu: Thiết lập quy trình rõ ràng từ khứ hồi, lưu trữ hiện hành đến lưu trữ lịch sử hoặc tiêu hủy văn bản khi hết giá trị.
2. Minh bạch hóa trách nhiệm và phối hợp hiệu quả
    - Rõ người, rõ việc: Phân định rõ ràng trách nhiệm của từng cá nhân, bộ phận (từ khâu tiếp nhận, soạn thảo, kiểm duyệt, ban hành đến lưu trữ).
    - Tối ưu quy trình phê duyệt: Áp dụng luồng xử lý văn bản tự động (workflow), giảm thiểu tối đa các "điểm nghẽn" và rút ngắn thời gian xử lý công việc giữa các phòng ban.
    - Giám sát tiến độ: Giúp cấp quản lý dễ dàng theo dõi quá trình triển khai, thực hiện văn bản, kiểm tra trạng thái xử lý văn bản và đánh giá hiệu suất làm việc (KPIs) của nhân viên một cách khách quan.
3. Đảm bảo an toàn thông tin và tuân thủ pháp lý
    - Phân quyền chặt chẽ: Kiểm soát quyền truy cập tài liệu (xem, sửa, xóa, chia sẻ) theo đúng chức năng, nhiệm vụ của từng vị trí, tránh rò rỉ thông tin mật.
    - Bảo mật và dự phòng: Thiết lập cơ chế sao lưu (backup) dữ liệu định kỳ, phòng ngừa các rủi ro mất mát do sự cố kỹ thuật hoặc thiên tai.
    - Tính pháp lý: Đảm bảo hệ thống lưu trữ tuân thủ các quy định hiện hành của pháp luật về văn thư, lưu trữ và an toàn thông tin doanh nghiệp.

## II. Mô hình tổng thể

1. Kiến trúc phân cấp (Hierarchy): Epic và Task/Sub-task
    - Ý nghĩa của Epic và Task:
        - Epic (Quản lý theo Dòng văn bản / Nhóm tài liệu): Epic đóng vai trò là các Luồng văn bản lớn hoặc Bộ hồ sơ hoặc Dự án tài liệu.
            - Ví dụ: Epic: "Văn bản đi", Epic: "Hồ sơ Pháp lý & Giấy phép", Epic: "Hợp đồng Nhà cung cấp".
        - Task / Issue Type (Từng văn bản cụ thể): Mỗi Task là một văn bản cần xử lý hoặc lưu trữ. Nên tạo các Issue Type riêng như: Văn bản Đến, Văn bản Đi, Tờ trình/Quyết định nội bộ.
        - Sub-task (Các bước thực hiện): Dùng cho quy trình phối hợp xử lý văn bản.
            - Ví dụ: Với Task "Hợp đồng mua sắm IT", Sub-task sẽ là: 1. Soạn thảo thô; 2. Thẩm định pháp lý; 3. Ký số cấp duyệt.

**Workflow**

Workflow phù hợp cho việc quản lý văn bản trong nhiều năm:

```text
    Draft → Review → Approved → Published → Archived
    ──────────────────────────────────────────────────
    Dự thảo → Xem xét → Chấp thuận/Phê duyệt → Phát hành/Ban hành → Lưu trữ/Lưu hồ sơ
```

Workflow này không chỉ phân loại mà còn quản lý trạng thái sống của văn bản, điều mà schema Jira thường dùng để mô hình hóa quy trình làm việc. Với kho văn bản, trạng thái “Archived” rất quan trọng vì nó giữ lịch sử mà không làm rối backlog hiện hành.

2. Mô hình phân loại bằng tính năng nâng cao của Jira
    - Để tìm kiếm và lọc (JQL) văn bản chính xác, chúng ta phân bổ cấu trúc dữ liệu như sau:

|Tính năng Jira|Khái niệm trong Quản lý Văn bản|Ví dụ thực tế|
|:---:|:---|:---|
|Version|Quản lý Năm hành chính hoặc Phiên bản sửa đổi của tài liệu hệ thống.|Năm 2026, Năm 2027 hoặc V1.0 (Ban hành), V2.0 (Sửa đổi) cho ISO.|
|Component|Phân loại theo Phòng ban chủ trì hoặc Khối nghiệp vụ.|Phòng Nhân sự, Phòng Kế toán, Ban Pháp chế, Ban Giám đốc.|
|Label|Phân loại theo Tính chất, Mức độ khẩn cấp hoặc Chủ đề linh hoạt.|Mat, Khan, Hoa-toc, Tuyen-dung, Kiem-toan.|
|Assignee|Người chịu trách nhiệm xử lý chính ở bước hiện tại.|Chuyên viên văn thư, Trưởng phòng phê duyệt.|

3. Quy trình xử lý (Workflow) cho một Văn bản (Task)
    - Mỗi Task (văn bản) sẽ đi qua một Workflow chuẩn hóa để đảm bảo tính phân công rõ ràng:
        - Mới tiếp nhận (To Do): Văn thư nhập liệu văn bản đến, đính kèm file scan, gắn Component và Label.
        - Đang xử lý/Xin ý kiến (In Progress): Chuyển giao cho các phòng ban được chỉ định xử lý nội dung.
        - Chờ phê duyệt (Under Review): Giao cho cấp quản lý duyệt (gắn kèm tính năng Approval của Jira nếu có).
        - Đã ban hành / Lưu trữ (Done): Văn bản hoàn thành, đóng lại để lưu trữ lâu dài.

### Mô hình kiến trúc

```text
Project: Quản lý văn bản
├─ Versions: Năm bắt đầu soạn thảo văn bản [2026, 2027, 2028]
├─ Epics: Chủ đề nội dung [TH văn bản liên quan đến HĐQT, BKS HISSC; liên quan đến quy định của CNS; thông tin triển khai của CNS; thông tin chỉ đạo, phản hồi của CNS]
├─ Components: Xuất xứ / nguồn [CNS_HĐTV, CNS_PC, CNS_NS, CNS_VP, CNS_ĐU, CNS_KTAT, HIS_HĐQT, HIS_BKS, Khác]
├─ Labels: Từ khóa tìm kiếm [NDDV, Báo_cáo, Triển_khai, Tham_khảo, Quy_định, Xin_ý_kiến, Phản_hồi, Làm_rõ, Giải_trình]
├─ Issues: Loại văn bản [bản nháp, bản dịch, bản rà soát, ghi chú xử lý, văn bản đến, văn bản đi]
└─ Sprint: Giai đoạn xử lý văn bản [GĐ_ban hành, GĐ xem xét, GĐ chuẩn bị, GĐ xin ý kiến]
```

- Project giữ toàn bộ kho văn bản trong một không gian thống nhất, còn versions đóng vai trò mốc thời gian của project.
- Epic, component, label là ba trục phân loại khác nhau, nên mỗi trục chỉ nên giữ một ý nghĩa ổn định để tránh chồng chéo.
    - Epic: Phân loại theo chủ đề
    - Component: Phân loại theo nguồn gốc
    - Label: Phân loại theo tính chất, mối liên hệ
- Issue link là mối quan hệ giữa các văn bản (Liên quan đến)

### Thành phần

#### Dịch vụ quản lý CNTT (HI-ITSM)
- Là phần mềm quản lý công việc hàng đầu cho phép kiểm soát các tác vụ, công việc đối với các hoạt động quan trọng của tổ chức, doanh nghiệp. Thông thường, các nhà quản lý sẽ gặp nhiều khó khăn trong việc xử lý và kiểm soát một lượng lớn thông tin. Để giải quyết vấn đề này, ứng dụng quản lý CNTT được xây dựng để tối ưu quy trình và giúp phối hợp công việc tốt hơn.

#### Tính năng
- Quản lý công việc: Cung cấp giao diện dễ sử dụng để khách hàng/đại lý gửi yêu cầu hoặc đề nghị hỗ trợ; tự động phân loại, chuyển đến đúng nhóm hoặc nhân sự phụ trách; theo dõi và đảm bảo các đề nghị được giải quyết trong thời gian cam kết.
- Quản lý qui trình: Cung cấp qui trình rõ ràng cho việc phê duyệt thay đổi, tích hợp lịch để theo dõi các thay đổi theo kế hoạch.
- Cơ sở tri thức: Lãnh đạo/ quản lý hoặc nhân viên có thể tự tìm kiếm các vấn đề đã từng thực hiện thông qua cơ sở tri thức của đơn vị đã được xây dựng, tích hợp; giảm thiểu đề nghị hỗ trợ thông qua tài liệu FAQ và hướng dẫn. 
- Tự động hóa: Tự tạo, cập nhật hoặc đóng các yêu cầu/đề nghị theo điều kiện cụ thể, thiết lập luồng công việc phù hợp với qui trình nội bộ.
- Báo cáo và phân tích: Đo lường hiệu suất nhân viên theo thời gian thực, cung cấp dashboard tổng quan về tình trạng tiếp nhận, xử lý các yêu cầu/đề nghị từ nội bộ hoặc phân công từ Lãnh đạo/ quản lý.

#### Nội dung thực hiện

1. Chuẩn bị tài nguyên
    - Máy chủ cài đặt Jira server Data center
    - Phân bổ dung lượng theo nhu cầu sử dụng

3. Điều chỉnh, bổ sung các thành phần của phần mềm
    - Workflow, Assigned user, Authorized

## Bộ quy ước chuẩn

Dưới đây là bảng chuẩn hóa summary cho từng loại văn bản trong Jira theo hướng dễ đọc, dễ tìm, và đủ thông tin để phân biệt nhanh. Mình giữ nguyên nguyên tắc chung: **bắt đầu bằng loại văn bản, sau đó là chủ đề, rồi nguồn hoặc mốc ngắn nếu cần**.

### Bảng chuẩn hóa summary

|---|---|---|---|

| Ghi chú | `Ghi chú - [Chủ đề] - [Nguồn/Mốc]` | `Ghi chú - Quy trình nội bộ - Q3` | Dùng cho note ngắn, ít cấu trúc hơn biên bản. |

### Quy tắc chung để áp dụng

- Dùng **một loại văn bản cố định** ở đầu summary.

- Phần cuối chỉ nên là **nguồn** hoặc **mốc phân biệt**, không nhét quá nhiều metadata.
- Nếu version đã thể hiện năm rõ ràng, summary không cần lặp lại năm trừ khi nó giúp phân biệt giữa các bản gần nhau.

## Nguyên tắc lọc

JQL nên đi từ **phạm vi lớn đến chi tiết**: project trước, rồi version, epic, component, label, và cuối cùng mới lọc theo text như summary hay description. Với kho văn bản, cách này giúp truy vấn vừa chính xác vừa dễ bảo trì.

<details><summary>Cụ thể</summary><blockquote><div markdown="1">

## Mẫu cơ bản

### Theo project
```jql
project = DOCS
```

### Theo năm
```jql
project = DOCS AND fixVersion = "2026"
```

### Theo chủ đề
```jql
project = DOCS AND epic = AI
```

### Theo xuất xứ
```jql
project = DOCS AND component = "Workshop-08"
```

### Theo label
```jql
project = DOCS AND labels = translation
```

## Mẫu kết hợp

### Tài liệu của năm 2026, chủ đề AI, nguồn Workshop-08
```jql
project = DOCS AND fixVersion = "2026" AND component = "Workshop-08" AND labels = summary
```

### Bản nháp cần xử lý
```jql
project = DOCS AND labels = draft AND status != Archived
```

### Bản cuối của một chủ đề
```jql
project = DOCS AND epic = AI AND labels = final
```

### Tài liệu chưa đủ metadata
```jql
project = DOCS AND (fixVersion is EMPTY OR component is EMPTY OR labels is EMPTY)
```

project = DOCS AND summary ~ "biên bản"

project = DOCS AND summary ~ "\"Bản dịch\""

project = DOCS AND summary ~ "AI workshop"

project = DOCS AND text ~ "AI"

## Tìm các bản liên kết với bản cũ

Nếu bạn dùng issue link để nối bản cũ và bản mới, có thể lọc các issue đã có liên kết  [atlassian](https://www.atlassian.com/software/jira/guides/jql/cheat-sheet).

```jql
project = DOCS AND issueLinkType is not EMPTY
```

Nếu muốn lọc riêng những bản có khả năng là bản thay thế:
```jql
project = DOCS AND issueLinkType = "supersedes"
```

## Sắp xếp kết quả

Bạn nên thêm `ORDER BY` để danh sách dễ đọc hơn  [atlassian](https://www.atlassian.com/software/jira/guides/jql/cheat-sheet).

### Mới nhất trước
```jql
project = DOCS ORDER BY created DESC
```

### Theo năm rồi mới đến ngày tạo
```jql
project = DOCS ORDER BY fixVersion DESC, created DESC
```

### Theo mức ưu tiên xử lý
```jql
project = DOCS AND status != Archived ORDER BY priority DESC, updated DESC
```

- `All docs`
- `Docs by year`
- `Docs by topic`
- `Docs by origin`
- `Drafts to review`
- `Final docs`
- `Missing metadata`
- `Linked to previous version`

Ví dụ:

```jql
project = DOCS AND fixVersion = "2026" ORDER BY created DESC
```

```jql
project = DOCS AND component = "Customer-A" ORDER BY updated DESC
```

```jql
project = DOCS AND labels = review AND status NOT IN (Done, Archived)
```

## Mẹo thực dụng

- Dùng `fixVersion` nếu bạn đã chốt version là năm.
- Dùng `component` cho nguồn, đừng dùng label để thay thế nguồn.
- Dùng `summary ~ ...` khi nhớ tên tài liệu hoặc loại văn bản.
- Dùng `labels` cho từ khóa phụ như `translation`, `draft`, `review`.
- Dùng `ORDER BY` để kết quả luôn có thứ tự ổn định.
